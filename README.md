## Installation

Run all commands from the repository root.

Use a Python version compatible with the project's `requires-python` setting in `pyproject.toml`.

### macOS / Linux

Create a project-local virtual environment:

```bash
python3 -m venv .venv
```

Install the package and development dependencies inside it:

```bash
./.venv/bin/python -m pip install --upgrade pip
./.venv/bin/python -m pip install -e ".[dev]"
```

Verify the interpreter and environment:

```bash
./.venv/bin/python -c "import sys; print('Interpreter:', sys.executable); print('Virtual environment:', sys.prefix != sys.base_prefix)"
```

The interpreter path should point inside this repository's `.venv`, and the virtual-environment check should print `True`.

### Windows PowerShell

Create and install into the project-local environment:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

Verify it:

```powershell
.\.venv\Scripts\python.exe -c "import sys; print('Interpreter:', sys.executable); print('Virtual environment:', sys.prefix != sys.base_prefix)"
```

### Optional activation

Activation makes shorter commands available in the current terminal.

macOS / Linux:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

After activation, use `python -m pip`, `python -m pytest`, and `python -m cluster_representation`.

The explicit interpreter commands below work without activation. No global installation, `sudo pip`, or `pip install --user` is needed.

Keep `.venv/` in `.gitignore`. Recreate the environment on each machine rather than committing or copying it.

## Run the workflow

From the repository root, run the complete configured pipeline.

macOS / Linux:

```bash
./.venv/bin/python -m cluster_representation --config config/default.yml
```

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m cluster_representation --config config/default.yml
```

Run an individual stage after its prerequisites have been saved.

macOS / Linux:

```bash
./.venv/bin/python -m cluster_representation \
  --config config/default.yml \
  --step generate_dataset
```

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m cluster_representation --config config/default.yml --step generate_dataset
```

Supported stages:

- `generate_dataset`
- `split_dataset`
- `fit_preprocessor`
- `train_model`
- `build_prototypes`
- `transform_test`
- `evaluate`

Each stage validates its prerequisite artifacts and reports missing or incompatible inputs.
`transform_test` processes every indicator generated by the configured
`nonconsent` range. Its scenario-specific outputs are saved under
`models/<model>/transformed/<scenario>/` or
`models/<model>/k_<selected-k>/transformed/<scenario>/` when cluster search is enabled;
evaluation reuses those saved outputs.

Existing artifacts are not overwritten unless `output.overwrite: true` is configured. Use a new `output.run_name` for a separate experiment.

All application implementation lives in `src/cluster_representation/`. The CLI and notebooks call the same stage functions.

## Constrained K-means cluster search

The K-means model configuration can use `cluster_search` to fit a supplied list
of cluster counts. For example:

```yaml
name: constrained_kmeans
parameters:
  random_state: 12345
  max_iter: 300
  n_init: 10
cluster_search:
  enabled: true
  candidates: [5, 6, 7, 8, 9, 10]
  selected_n_clusters: 5
constraints:
  type: minimum_cluster_size
  min_cluster_size: 100
```

Candidate counts must be unique positive integers; nonconsecutive values are
valid. Candidates that do not satisfy `K * min_cluster_size <= n_train` are
recorded as skipped in the comparison report. Each feasible candidate is fitted
independently on the same saved training split and fitted preprocessing. Scores
are calculated using training data only, and the same deterministic sample is
used for silhouette comparisons. Each candidate's model, fitted training
assignments, metadata, and training-median prototypes are saved in their own
`models/constrained_kmeans/k_<K>/` directory.

`selected_n_clusters` may be a positive candidate integer or `auto`. An
integer always selects that candidate, regardless of its relative metric
scores. `auto` requires enabled search and ranks eligible candidates by the
average ranks of silhouette (descending), Davies–Bouldin (ascending), and
Calinski–Harabasz (descending). Ties in metric values receive average ranks;
the lowest mean rank wins, with smaller requested `k` breaking a score tie.
Training failures, unavailable/non-finite metrics, and hard-constraint
violations are excluded and reported. Automatic selection fails explicitly if
no candidate is eligible.

The resolved candidate is used for test assignment and replacement; changing
the selected candidate does not refit candidate models. If a fixed candidate
was skipped or failed, training stops with an explicit error. The training
notebook displays the saved comparison table, including automatic selection
scores and the chosen candidate, and the package-generated score plot. Legacy
single-model configurations with `parameters.n_clusters` and no
`cluster_search` remain supported.

The evaluation notebook writes `metrics/combined_evaluation.csv` and
`metrics/combined_evaluation.parquet`. Search runs include one row for each
successfully trained candidate and configured non-consent scenario. Training
cluster metrics are reused from the candidate comparison, and test replacement
errors are calculated from each saved candidate model and prototype without
refitting. The returned notebook table uses readable labels and displays
unavailable values as `N/A`; the exported files retain machine-readable column
names and null metric values.

The evaluation stage also writes `tables/overall_comparison.md` in the current
run directory. It reports the selected constrained K-means candidate and
configured non-consent scenario; AP and F1 are shown as unavailable because
they are not calculated by this clustering workflow. The table's time column
is model fitting time in seconds. Its MAE and MAPE columns are calculated only
over replaced rows and configured features; MAPE excludes cells whose original
value is zero. The detailed scenario results retain the all-test-row MAE and
per-feature MAE metrics for compatibility.

The evaluation stage also writes `tables/cluster_selection_comparison.md`,
with one row for each successfully trained cluster-count candidate. It reads
training metrics and `training_time_seconds` from saved candidate metadata;
metric winners are ranked at full precision within each equivalent model
configuration, and ties are all bolded.

## Spectral co-clustering

To run the unconstrained scikit-learn `SpectralCoclustering` model, point the
model name in `models.run` in `config/default.yml` and map it to its model
configuration under `models.configs`. For example:

```yaml
models:
  run:
    - constrained_kmeans
    - spectral_coclustering
  configs:
    constrained_kmeans: models/constrained_kmeans.yml
    spectral_coclustering: models/spectral_coclustering.yml
```

Only models listed in `models.run` are executed, in that order. Keep each
model's parameters and search settings in its mapped configuration file. The
spectral model configuration supports fixed or automatic selection:

```yaml
name: spectral_coclustering
parameters:
  random_state: 12345
  n_init: 10
cluster_search:
  enabled: true
  candidates: [5, 6, 7]
  selected_n_clusters: auto
```

Set `selected_n_clusters` to a candidate integer (for example `5`) to use a
fixed count. Spectral co-clustering has no minimum-cluster-size constraint;
constraint applicability is saved as `not applicable`. Its `n_init` and
`random_state` parameters are passed to scikit-learn; `max_iter` is not
accepted because `SpectralCoclustering` does not expose that parameter.

The shared, training-fitted preprocessing remains unchanged. The model then
fits its own training-only min/max conversion to finite nonnegative values,
removes constant/all-zero feature columns from the spectral fit, and stores
that preprocessing with each candidate. All-zero training rows are omitted
from the spectral fit and assigned to the largest fitted row cluster;
all-zero future rows use the same deterministic rule. Saved active column
labels retain scikit-learn's zero-based labels; dropped feature columns use
`-1` in `column_labels.parquet`.

The registered `constrained_coclustering` and
`robust_constrained_coclustering` entries remain unimplemented templates;
selecting either currently raises `NotImplementedError`.

Because `SpectralCoclustering` has no `predict`, future customers are assigned
to the nearest centroid of the fitted row memberships in the model's saved,
nonnegative feature space. The model and `column_labels.parquet` are saved
separately per candidate. For fair customer-cluster comparisons, silhouette,
Davies–Bouldin, and Calinski–Harabasz are calculated in the shared fitted
preprocessing output space, not the model-specific nonnegative space.
Candidates that exceed the active matrix dimensions or otherwise cannot be
fit are reported as failed and are ineligible for automatic selection.
AP/F1 remain unavailable because this workflow has no ground-truth customer
class labels.

`constrained_coclustering` and `robust_constrained_coclustering` remain
configuration-only templates: their `fit()` and `predict()` methods explicitly
raise `NotImplementedError`.

## Notebooks

Install development dependencies into `.venv` before starting Jupyter. They must include JupyterLab and `ipykernel`.

Launch Jupyter using the virtual environment's Python, with `notebooks/` as the working directory.

macOS / Linux:

```bash
cd notebooks
../.venv/bin/python -m jupyterlab
```

Windows PowerShell:

```powershell
Set-Location notebooks
..\.venv\Scripts\python.exe -m jupyterlab
```

Select the Python kernel belonging to this repository's `.venv`.

If it is not listed, register it from the repository root:

macOS / Linux:

```bash
./.venv/bin/python -m ipykernel install \
  --prefix .venv \
  --name synthetic-cluster-representation \
  --display-name "Python (.venv — Synthetic Cluster Representation)"
```

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m ipykernel install --prefix .venv --name synthetic-cluster-representation --display-name "Python (.venv - Synthetic Cluster Representation)"
```

Restart Jupyter and select that kernel. Registration is local to `.venv`.

To inspect the interpreter used by a notebook:

```python
import sys

print(sys.executable)
```

It should point inside the repository's `.venv`.

Notebooks load `../config/default.yml`, call package stage or reporting
functions, and display returned summaries. All processing, model logic,
validation, plotting, and artifact saving remain in `src/`.

Notebooks must not install dependencies, modify `sys.path`, duplicate implementation, or depend on variables from other notebooks.

Run stages in order. Each stage loads its saved prerequisites.

To choose another configuration, set `CLUSTER_REPRESENTATION_CONFIG` before launching Jupyter. An absolute path avoids working-directory ambiguity.
